# Дашборд в Yandex DataLens поверх витрин

Ноутбук `notebooks/ab_experiment_analysis.ipynb` выгружает в `data/marts/` три CSV.
Этот файл — что с ними делать в DataLens и почему формулы написаны именно так.

## Что в витринах

| файл | гранулярность | для чего |
|---|---|---|
| `mart_daily.csv` | день × вариант × платформа | динамика и разрезы, основной источник дашборда |
| `mart_users.csv` | пользователь | распределения, когорты, пересчёт метрик на лету |
| `mart_results.csv` | метрика × метод | готовые эффекты и доверительные интервалы |

`mart_daily.csv` содержит **аддитивные** величины: `gmv`, `orders`, `sessions`,
`assigned_users`. Отношения в витрину не кладутся — их считает BI. Причина в том, что
среднее не аддитивно: если посчитать `gmv_per_user` по каждому дню и усреднить по дням,
получится не то же самое, что `SUM(gmv) / SUM(assigned_users)` за период, когда дни разного
размера. Любая фильтрация в BI меняет набор строк, поэтому отношение обязано пересчитываться
из сумм, а не агрегироваться из готовых средних.

Исключение — `active_users`: `COUNT(DISTINCT user_id)` не восстанавливается из суточных
сумм (один человек заходит несколько дней и посчитается дважды). Эта колонка лежит готовой
и по дням не суммируется.

## Шаги

**1. Подключение.** DataLens → Подключения → *Файлы* → загрузить три CSV. Разделитель `,`,
кодировка UTF-8, первая строка — заголовок. Для продовой версии вместо файлов ставится
подключение к ClickHouse или PostgreSQL, а витрины становятся материализованными
представлениями; остальная часть инструкции не меняется.

**2. Датасет** на `mart_daily`. Типы: `day` — целое, `variant` и `platform` — строки,
остальное — числа. `assigned_users` пометить агрегацией **«не агрегировать»**: оно
дублируется по дням, и сумма по дням даст размер группы, умноженный на число дней.

**3. Вычисляемые поля** — пишутся через `SUM`, а не через готовые столбцы:

```sql
-- размер группы: максимум, а не сумма, потому что значение повторяется в каждом дне
Размер группы   = MAX([assigned_users])

-- ключевые отношения: сумма делится на сумму
GMV на пользователя    = SUM([gmv]) / MAX([assigned_users])
Заказы на сессию       = SUM([orders]) / SUM([sessions])
Средний чек            = SUM([gmv]) / SUM([orders])
Конверсия в покупателя = SUM([buyers]) / MAX([assigned_users])
```

Эффект к контролю — через `LOD`-выражение с фиксацией измерения, иначе при фильтрации
по платформе база сравнения уедет вместе с фильтром:

```sql
Контроль, GMV/польз. = SUM([gmv] FIXED [platform] WHERE [variant] = 'control')
                     / MAX([assigned_users] FIXED [platform] WHERE [variant] = 'control')
Эффект, %            = 100 * ([GMV на пользователя] / [Контроль, GMV/польз.] - 1)
```

**4. Чарты.**

| чарт | тип | поля |
|---|---|---|
| Выручка по дням | линейный | X `day`, Y `GMV на пользователя`, цвет `variant` |
| Разрез по платформам | столбчатый | X `platform`, Y `GMV на пользователя`, цвет `variant` |
| Заказы на сессию | линейный | X `day`, Y `Заказы на сессию`, цвет `variant` |
| Эффект и CI | столбчатый, источник `mart_results` | X `метрика`, Y `эффект, %`, подписи — границы CI |
| KPI | индикатор | `Эффект, %` и `p-value` из `mart_results` |

**5. Дашборд.** Селектор `platform` (мультивыбор) и селектор диапазона `day`, оба
привязаны ко всем чартам. Сверху — индикаторы, под ними динамика, ниже разрезы.

## Две вещи, которые на дашборде легко сделать неправильно

**Кумулятивная кривая как основание для решения.** Накопленная выручка почти всегда
расходится к концу просто потому, что накапливается шум, и соблазн остановить тест в момент
расхождения велик. Ежедневное подглядывание — это множественные сравнения во времени: при
проверке каждый день две недели доля ложных срабатываний растёт примерно с 5 % до 20 %.
Если нужна возможность останавливаться досрочно, это делается явно — mSPRT или group
sequential design с альфа-спендингом, а не глазами по графику. На дашборде поэтому стоит
дневной ряд, а под ним подпись об этом.

**Фильтр по сегменту с теми же порогами.** Селектор платформы режет выборку, но порог
значимости остаётся 0.05, а сегментов много. Поправка на множественность (Холм) считается
в ноутбуке и лежит в `mart_results`; на дашборде сегментные выводы помечаются как
разведочные, а решение принимается по заранее зафиксированной первичной метрике.
