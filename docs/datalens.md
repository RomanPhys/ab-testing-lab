# Дашборд в Yandex DataLens поверх витрин

Ноутбук `notebooks/ab_experiment_analysis.ipynb` выгружает в `data/marts/` три CSV. Здесь написано,
что с ними делать в DataLens и почему формулы именно такие.

## Что в витринах

| файл | гранулярность | для чего |
|---|---|---|
| `mart_daily.csv` | день × вариант × платформа | динамика и разрезы, основной источник дашборда |
| `mart_users.csv` | пользователь | распределения, когорты, пересчёт метрик на лету |
| `mart_results.csv` | метрика × метод | готовые эффекты и доверительные интервалы |

В `mart_daily.csv` лежат только аддитивные величины (`gmv`, `orders`, `sessions`, `assigned_users`).
Отношения в витрину не кладу, их считает BI. Дело в том, что среднее не аддитивно. Если посчитать
`gmv_per_user` за каждый день и усреднить по дням, это не совпадёт с `SUM(gmv) / SUM(assigned_users)`
за период, когда дни разного размера. Любой фильтр в BI меняет набор строк, поэтому отношение нужно
каждый раз пересчитывать из сумм, а не собирать из готовых средних.

Исключение одно, `active_users`. `COUNT(DISTINCT user_id)` из суточных сумм не восстановить, потому что
человек, который заходил несколько дней, посчитается несколько раз. Эта колонка лежит готовой, и по дням
её не суммируют.

## Шаги

### 1. Подключение

В DataLens открыть Подключения, выбрать «Файлы» и загрузить три CSV. Разделитель `,`, кодировка UTF-8,
в первой строке заголовок. В проде вместо файлов будет подключение к ClickHouse или PostgreSQL,
а витрины станут материализованными представлениями. Остальные шаги от этого не меняются.

### 2. Датасет

Датасет строится на `mart_daily`. `day` целое, `variant` и `platform` строки, остальное числа.
Для `assigned_users` поставить агрегацию «не агрегировать». Значение повторяется в каждом дне,
и сумма по дням даст размер группы, умноженный на число дней.

### 3. Вычисляемые поля

Все отношения пишутся через `SUM`, готовые столбцы со средними не используются.

```sql
-- размер группы: берём максимум, потому что значение повторяется в каждом дне
Размер группы   = MAX([assigned_users])

-- отношения: сумма делится на сумму
GMV на пользователя    = SUM([gmv]) / MAX([assigned_users])
Заказы на сессию       = SUM([orders]) / SUM([sessions])
Средний чек            = SUM([gmv]) / SUM([orders])
Конверсия в покупателя = SUM([buyers]) / MAX([assigned_users])
```

Эффект относительно контроля считается через `LOD`-выражение с фиксацией измерения. Без этого при
фильтре по платформе база сравнения уедет вместе с фильтром.

```sql
Контроль, GMV/польз. = SUM([gmv] FIXED [platform] WHERE [variant] = 'control')
                     / MAX([assigned_users] FIXED [platform] WHERE [variant] = 'control')
Эффект, %            = 100 * ([GMV на пользователя] / [Контроль, GMV/польз.] - 1)
```

### 4. Чарты

| чарт | тип | поля |
|---|---|---|
| Выручка по дням | линейный | X `day`, Y `GMV на пользователя`, цвет `variant` |
| Разрез по платформам | столбчатый | X `platform`, Y `GMV на пользователя`, цвет `variant` |
| Заказы на сессию | линейный | X `day`, Y `Заказы на сессию`, цвет `variant` |
| Эффект и CI | столбчатый, источник `mart_results` | X `метрика`, Y `эффект, %`, в подписях границы CI |
| KPI | индикатор | `Эффект, %` и `p-value` из `mart_results` |

### 5. Дашборд

Два селектора, `platform` (мультивыбор) и диапазон `day`, оба привязаны ко всем чартам. Наверху
индикаторы, под ними динамика, ещё ниже разрезы.

## Где на дашборде легко ошибиться

### Решение по кумулятивной кривой

Накопленная выручка к концу почти всегда расходится, просто потому что копится шум, и очень хочется
остановить тест в момент расхождения. Но если смотреть на график каждый день, это множественные
сравнения во времени. При ежедневной проверке в течение двух недель доля ложных срабатываний растёт
примерно с 5 % до 20 %. Если нужна досрочная остановка, её надо закладывать явно (mSPRT или group
sequential design с альфа-спендингом), а не решать на глаз по графику. Поэтому на дашборде стоит
дневной ряд и под ним подпись про это.

### Фильтр по сегменту с тем же порогом

Селектор платформы режет выборку, а порог значимости остаётся 0.05, хотя сегментов много. Поправку
на множественность (Холм) я считаю в ноутбуке, она лежит в `mart_results`. На дашборде выводы по
сегментам помечены как разведочные, а решение принимается по первичной метрике, которую зафиксировали
заранее.
